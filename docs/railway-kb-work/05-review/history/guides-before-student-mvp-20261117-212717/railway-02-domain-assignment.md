## 0. 2026-11-16 执行更新：复用归档结果，保持原目标

用户要求约节约10%成本、提高效率，质量不变。通用执行规则见[指导书一第0节](railway-01-source-expansion.md)。本书五领域、逐篇唯一主归属、来源核验和真实系统映射要求均保留。

1. **不要重新分类已验证且没有变化的全文。** 首次分类必须读完整正文；复用时检查文档哈希、领域规则和已有判断依据。仅补充内容且主对象不变时，审核变更涉及的主题；主对象、结论或领域规则变化时重新全文判断。
2. **一次读取系统清单，在当前批次内复用。** 上传前按doc_id、内容哈希、目标库及管道版本查现有记录；同批无外部变动时不对每一篇重新拉取全部75份历史文件。发生上传、停用、改版或发现外部变化后刷新相关状态，不能只相信旧清单。
3. **正式库和隔离库分别记状态。** DOC0022/23已有隔离试切的历史证据，应关联核对，不从头上传重做，也不能把隔离通过写成正式通过。原文、管道或源效力变化时仍须重测。
4. **不要同时维护多份互相矛盾的“当前状态”。** 复用现有 `document-register.json`，把来源、结构、隔离试切、正式导入、检索验收分别记录；已有历史快照保持原样。批末用本地工具更新相关Markdown展示，禁止将 `count_as_valid=true` 直接当成最终通过。
5. **每批最多5篇的写入边界不变。** 本地只读校验可以一次处理整批；上传和状态写回按依赖顺序执行，避免竞争覆盖、重复上传和反复嵌入。原件与旧版本继续保留。

当前 `dataset-map.md` 将五个领域指向同一正式原库，另有五个隔离试验库。这里是当前记录，不代表已完成“五个正式领域知识库”。执行者先核对已有用户决定和映射，一次解决目标口径；若没有改变目标的明确依据，就继续保留原五领域知识库交付要求，不把这个问题留到最终验收才发现。不要因提速新建重复库、擅自提升隔离库权限或替换原库。

## 1. 完整执行提示词

你是铁路知识库资料归档执行者。请按照本文件实际检查并归档所有待处理 Markdown，不要只提出分类建议。先读项目 `AGENTS.md` 和指导书一的进度、基线、来源登记表、文档登记表，再执行以下步骤。

本任务把业务资料分成五个铁路领域。不能把“PDF、Markdown、论文、FAQ”当成知识库领域，也不能只创建五个空库就宣布完成。每篇合格文档必须有且只有一个主领域；跨领域关系用辅助领域和来源关联记录。不要通过跨库复制同一篇资料增加文档统计数量。

不要删除原知识库，不清空文档，不更改现有用户权限，不让用户不可访问原资料。知识库创建和上传只有在用户已授权且当前工具有访问能力时执行；否则完成本地归档和完整映射准备，明确标记远端操作未执行，不能伪造知识库 ID 或上传成功记录。

先本地归档，后精修结构，最后正式上传解析。本阶段如果已经连接系统，可以核验或创建目标领域知识库，但不要把未经精修的草稿批量触发解析。系统不能暂停解析时，把上传动作延后到指导书三。

每批处理最多 5 篇；首次归档每篇读完整正文，不只看文件名，已核验结果按第0节复用。遇到无法判断的资料进入待复核队列，继续处理其余文档。

| CL | 铁路机车车辆与运用检修 | 车辆结构、走行部、制动、车载牵引设备、车辆检测和检修 | 行车调度安排归 YS；车载信号控制机制归 XH |

判断顺序固定如下：

1. 用一句话写出“本文主要回答哪个对象的什么问题”。
2. 对照表格确定核心对象；标题与正文冲突时以实际正文和原始来源为准。
3. 统计各领域覆盖的有效知识点，不统计目录、引用清单和背景套话。
4. 一个领域占比约 60% 以上且核心结论属于该领域，选其为主领域。60% 是辅助规则，不是自动分类模型参数。
5. 没有明显多数时，以文章主要结论和使用场景确定主领域，其他记辅助领域。
6. 若仍无法确定，写出两个候选领域及理由，进入待复核，禁止随机选一个。

## 4. 所有 Markdown 如何处理

“所有 Markdown”指任务登记的业务知识资料，不包括代码 README、开发说明、这三份指导书、进度表、模板和自动生成的 Wiki。

对每个 doc_id 依次执行：

1. 查文档登记表并打开完整正文，确认不是重复或待核验资料。
2. 检查来源、版本、适用范围；缺少关键项则退回指导书一。
3. 按上一节确定主领域和辅助领域，记录来自正文的判断依据。
4. 移入对应 `03-domains/<代码>/`，保留 doc_id，不因换目录重编号。
5. 更新文档登记表和领域登记表，保证路径一致。
6. 标记“已归档、待结构精修”，交给指导书三。

综合文献原则上保留一个主副本。只有原文章节确实独立、需要不同访问范围或不同检索组织时才拆成章节文件；各文件必须保留同一来源 ID、计数归并 ID 和原章节位置，统计时仍只算一份原始资料。不要为凑五个库的数量机械拆文。

相同标题但不同版本不是直接删除的重复项。分别登记版本、效力、替代关系；无法确认先后和效力时进入待复核。不能默认“发布日期最新”就自动适用于所有对象和线路。

## 7. 上传交接与可重复执行

本阶段完成待导入清单，实际上传在指导书三精修与试切通过之后执行。`import-register.md` 至少记录：

`doc_id、主领域、MD 路径、内容 SHA-256、目标知识库实际 ID、系统文档实际 ID、资料版本、管道版本、结构复核状态、上传状态、解析状态、检索验收状态、错误、更新时间`。

同一个 doc_id、同一份内容哈希和同一目标库已经上传成功时，重跑不能再次新建一份。内容改变时先核对系统是否支持原文档更新；按实际能力更新或建立替代版本，并记录前后关系。管道版本改变即使文件哈希不变，也要重新安排解析验收。不要先删除旧文档再尝试新上传。

只有“文件存在”不代表上传成功；只有“上传成功”不代表解析成功；只有“解析成功”不代表检索正确。必须分别记录三个状态。无法读取真实状态时写“未核验”。

五领域是内容分类，同一领域内可按内容选择不同切片管道。不要把领域和解析格式绑死。现有示例 `example/railmind-demo/pipelines/` 可用于了解管道结构，但其中模型、资源和知识库绑定必须在目标空间重新核对，不能原样套用。

## 8. 数量对账和完成条件

分类结束时列出五个领域的有效文档数、独立来源数、待复核数和覆盖主题。五领域有效数的合计必须等于本阶段已归档有效总量，跨域标签不能重复加数。

初始分配可按每领域约 20% 制定搜集计划，然后根据真实问题和来源情况调整。不能为了凑比例，把无关资料塞进缺资料的库；领域过薄时回到指导书一补资料。

- [ ] 每个合格业务 MD 都有唯一主领域和真实路径。
- [ ] 无丢失、无同一主副本重复归档、无资料版本被静默覆盖。
- [ ] 每条跨域归属都有理由，不能把全部文件贴上五个标签。
- [ ] 五领域都有资料；空领域和覆盖不足领域有明确补充清单。
- [ ] 领域数量与有效总量对得上，未重复计算拆分资料。
- [ ] 本地归档、远端建库、上传、解析分别报告，未执行的不得标为完成。
- [ ] 未经结构精修的文件没有作为正式切片成果通过验收。

最终输出一份 `domain-acceptance.md`，写清“已归档多少、待复核多少、各领域多少、已验证哪些真实知识库、下一批精修哪些 doc_id”。
