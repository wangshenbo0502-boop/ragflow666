# 指导书三：文档语义结构化预处理与精确切片

> **2026-11-16 最新范围纠正，优先于旧提示词和历史报告：** 用户要的是把文档按原文语义整理成结构清晰的Markdown，方便后续切片，不是建设Wiki。取消Wiki主题规划、跨文档百科归纳、页面生成、编译、刷新、Wiki检索及Wiki验收。不是暂缓，也不列为未完成事项。保留原件、现有合格主稿和历史记录，不因此删除已有系统功能或成果。

## 使用目标：把原文整理清楚，不另造一套知识内容

执行顺序为：**原始文档 → 忠实的Markdown整理 → 语义结构精修 → 结构核对 → 语义切片 → 真实入库 → 检索验收**。

“语义结构化预处理”具体要完成：

1. 恢复章、节、条、款的真实层级，将排版断行修复为正常段落，删除页眉页脚等噪声。
2. 按原文实际主题组织标题；一个独立问题或知识点有清楚的边界，不按固定字数硬拆，也不把每个句子都变成小标题。
3. 让条件、结论、例外、禁止事项保持在同一语义单元中；保留步骤顺序、依赖关系和跨条引用。
4. 整理列表、表格、合并单元格、表头、单位和表注，让每段内容能被正确理解和定位。
5. 保存原条款号、原始来源、版本及页/段/单元格定位。新增编辑标题不得冒充原文标题。
6. 忠实保留有效原文，不用摘要替换全文，不凭常识扩写规章，不为了“百科风格”合并不同文献或编造常见问题。资料内容扩充仍按指导书一取得来源后进行，与本阶段结构整理分开记录。

例如，原文同一条规定包含“适用对象、条件、要求、但书”，应整理成一个清楚的小节，内部用段落或标签区分；不能把但书拆成没有主体的单独片段。表格一行只有在带齐适用表头、单位和必要表注后才可独立切片。预处理先把边界表达清楚，实际切片仍由后续管道完成并核验，不在此阶段反复生成另一套百科文章。

### 0.3 语义审查按包处理，覆盖不能减少

- 先校准一个5项审查包，随后同一原表/共同条件的5～10项可以合并为一个模型请求。遇到长项或复杂合并单元格就减少包内项数，不截断源内容。输入限制用实际模型预算，优先保证每项完整。

## 3. 阶段 A：先调整文档结构

### A1. 读完整文档，列知识点清单

不要一边只读开头一边改全文。首次处理先完整阅读并列以下表格；续跑时按第0节复用已有完整阅读与知识点清单，只重审变化及其依赖，不反复重建同一清单：

| 知识点 ID | 要回答的问题 | 对象与条件 | 原文范围 | 依赖内容 | 建议小标题 |
| --- | --- | --- | --- | --- | --- |
| DOC0001-K01 | 按实际填写 | 按实际填写 | 来源、页/条/段 | 例外、表注、前置步骤 | 具体、可辨认 |

知识点 ID 保持稳定；后续修订不把同一 ID 分配给另一知识点。知识点不是新增文献，不能用于凑三至四倍文档量。

### A2. 统一标题层级

1. `#` 只出现一个，写具体文档名称。
2. `##` 表示主题组或原文章节。
3. `###` 表示一个完整知识点，例如“某对象的适用条件”，不要全部写成“说明”“其他”。
4. `####` 仅在一个知识点确有可独立检索的子主题时使用；不能为了排版把“条件”“例外”随意升成独立标题。
5. 同一知识点内部优先用加粗标签写“对象与条件、核心内容、例外、来源”，避免切片器把每个标签拆成一片。
6. 标题层级不跳级，不使用仅靠字体加粗伪装的标题，不保留与正文错配的目录。

原文条款编号是证据定位的一部分，必须保留；编辑用标题可以增加，但不能冒充原文标题或重新编号原文条款。

### A3. 拆分和合并的判断规则

逐段问：换一个独立问题是否会需要这段内容？

- 两段回答不同的问题，且各自有完整对象、条件和结论：拆成两个知识点。
- 一段是结论，另一段是该结论成立的前提、限制或例外：保留同一知识点。
- 一个长列表列举相互独立的故障现象：可按现象拆；每片补回适用对象和来源。
- 一个编号列表是一套有先后依赖的操作步骤：不能把每一步当成无上下文的独立知识点。
- 一段只有“按上述要求”“同前”“见表”：定位实际指代，补回必要的明确对象；不能自行推测。
- 两个段落虽然很短，但主题不同：不能只为了凑长度合并。
- 同一主题来自不同版本、设备或线路条件：分别组织并显式标记，不能混写成一个通用结论。

### A4. 清理格式，但不改变含义

去除重复页眉页脚、广告、导航、断行乱码和重复目录。删除的是噪声，不是原文的条件、否定词、数字或来源信息。

保留单位、公式变量解释、上下标、表注、图例、编号和引用位置。表格改为规范 Markdown 表格；合并单元格展开时补齐每行适用的组名。复杂表格无法无损转写时保留原图/原表定位，并写清可核验的文字说明，标记待复核，不凭空补空白值。

图片不能只留下“见图”；补充原图支持的文字说明和来源。扫描文字逐项核对否定词、阈值和单位。不能把图像描述模型生成的猜测当成原文。

### 复核未通过记录的处理

**核心内容：** 退回修改。退回原因和修改要求须来自对应复核记录。

**来源定位：** DEMO-S01，“复核”段。演示来源，不作真实证据。

注意：例子没有为了字数编造审核时限、责任人或审批层级。真实执行时所有 DEMO 内容都必须换成真实原件支撑的内容。

### A6. 结构通过条件

每篇逐项检查：标题层级正确；每个知识点有清晰对象；条件和例外紧邻结论；流程依赖完整；表格单位和表注完整；来源可定位；无新增无依据事实；无未解释指代；修改前后有效内容未丢失。

有任一影响事实或语义的缺陷，标记“待精修/待复核”，不得进入正式切片。

## 4. 阶段 B：定义预期切片

先为每个知识点写预期切片，再对照系统输出。预期切片是验收样本，不是声称已上传的系统文档。

每片至少能表达：文档标题、所属主题、知识点名称、对象与条件、完整核心内容、必要例外、来源定位。上级标题和条件若没有被系统自动携带，需要在正文中明确补入。

建议审计字段如下，它们是任务记录字段，不保证都是系统现有字段：

```json
{
  "doc_id": "真实文档ID",
  "knowledge_point_id": "稳定知识点ID",
  "domain_code": "GW/XH/GD/CL/YS中的一个",
  "heading_path": ["文档标题", "主题", "知识点"],
  "source_ids": ["真实来源ID"],
  "source_location": "原文章节/条款/页码/网页定位",
  "source_version": "真实版本或待核验",
  "text": "可独立理解的完整切片正文"
}
```

不要把这段示例 JSON 当作可直接调用的 API 请求。系统缺字段时保存在外部审计清单和必要的正文前缀中。

### 各类内容的边界

| 内容 | 基本切片单位 | 必须一同保留 |
| --- | --- | --- |
| 概念原理 | 一个概念或因果关系 | 对象、必要定义、适用边界 |
| 条款规定 | 一条完整规定或可独立理解的款项 | 原编号、前提、限定词、例外 |
| 操作流程 | 一个完整短流程或有清晰入口出口的阶段 | 前置条件、步骤依赖、结束条件 |
| 故障案例 | 一个案例或可独立理解的分析部分 | 设备与场景、现象、证据、结论边界 |
| 表格 | 完整小表或具有共同表头的一组行 | 表名、表头、单位、分类条件、表注 |
| 问答 | 一对真实可证的问题和答案 | 适用条件与来源 |
| 论文 | 一个方法、结果或结论知识点 | 研究条件、样本/场景、局限、来源 |

### 长度规则

优先按语义边界切，长度只用于发现异常。初始可将约 300～700 tokens 作为普通文本检查区间，短而完整的知识点允许更短。超过约 900 tokens 时必须复核是否包含多个主题；这不是模型最大输入长度，也不是当前系统保证的上限。

实际安全长度必须以所配置嵌入模型和重排模型的真实输入上限、实际 tokenizer 计数为准，标题和来源前缀也计入预算。不能把汉字数当成 tokens，不能只凭模型名字猜上限。

超长知识点的处理顺序：先找可独立的子问题 → 每个子片补回共同前提 → 保留父知识点关联和原文位置 → 再验证长度。不可拆且超出模型输入预算时，标记阻塞，设计可核验的概述加原文关联或调整实际管道后再验收；不得静默截断，也不得仅仅调大切片数值假装问题解决。

默认不跨知识点复制尾部文本。确需补上下文时复制必要条件或标题，并计入长度；不要用统一重叠百分比把相邻知识点混成一片。

## 5. 阶段 C：在当前项目中试切

截至本任务检查工作树时，可核验的路径如下。执行者须以当时实际代码为准，不把本表当作永远不变的接口说明。

| 项目路径 | 已观察到的能力或限制 | 执行注意事项 |
| --- | --- | --- |
| `internal/parser/parser/markdown_parser.go` | Markdown 结构解析入口 | 解析结构不等于语义完整性自动验证 |
| `internal/ingestion/component/chunker/manual.go` | 手册切片按标题归组；该路径不应用标题族的 token cap，忽略不适用的相关参数 | 不能承诺加 `chunk_token_cap` 就能限制 ManualChunker 长度 |
| `internal/ingestion/component/chunker/title.go`、`group.go`、`hierarchy.go` | 标题识别及分组/层级路径 | 配置和实际标题粒度要通过样本验证 |
| `internal/ingestion/component/chunker/token.go` | token 分段和合并路径；单个超预算单元不会自动安全细拆 | 不能依赖后续截断解决过长语义单元 |
| `internal/parser/chunk/options.go` | 内部通用 chunk 库部分长度选项使用 Unicode 字符数 | 不要把这里的参数与管道 token 参数混用 |
| `example/railmind-demo/pipelines/02-manual.json` | 现有手册类管道结构示例 | 仅参考结构；复制后核对实际字段、资源绑定和发布版本 |

具体执行步骤：

1. 首批选 5 篇，尽量各领域一篇，并覆盖条款、列表、表格、长段、跨段条件等情况；不足覆盖时补充下一批。
2. 保存原配置记录，为试验建立独立草稿管道或已授权的测试配置，不能直接覆盖所有生产库配置。
3. 对规范 Markdown 优先试验标题分组/层级方案。核对三级标题是否真正形成知识点边界，不盲填 `hierarchy` 数字。
4. 如果当前 UI 或管道不支持所需操作，记录实际限制；先完成预期切片，不编造“语义切片”开关。
5. 运行真实解析，检查解析预览，再导出或逐片读取最终结果。
6. 在 `chunk-review.md` 将实际片段与预期知识点逐一比对，记录实际文档 ID、切片 ID和管道版本。
7. 若整篇只生成一片，检查标题是否被识别、层级是否过粗、是否用错 OneChunker 或配置。
8. 若条件和结论分离，先调整标题与段落结构，再核对分组规则；不能只增加随机重叠。
9. 若表头丢失或列表乱序，退回解析/结构整理检查，不能直接交给大模型自由补齐。
10. 修正后重跑同一测试集，通过再扩大到其余文档。

本阶段以配置和资料整理为主。如确需改 Go 解析或切片代码，先定位真正负责该行为的路径并遵守项目测试要求；例如针对切片包运行 `bash build.sh --test ./internal/ingestion/component/chunker/...`。这只是代码修改时的验证要求，本指导书交付不代表已运行该测试。

## 6. 阶段 D：正式上传与切片检查

结构和试切通过后，按指导书二的映射每批上传最多 5 篇，记录真实系统 ID、内容哈希、管道发布版本。确认状态完成再检查切片。不要使用未经核验的 API 路径或复制其他空间的 ID。

每篇至少检查：第一片、最后一片、最长片、最短片，以及所有含表格、数值阈值、否定词、例外和步骤依赖的片段；不足 10 片的文档检查全部。抽检结论必须写明检查数量，不能据此声称全量每片均已人工核验。

对每个检查片段回答六个问题：

1. 单独读能否知道“什么对象、什么条件、什么结论”？
2. 是否只围绕一个核心知识点，没有混入不相关主题？
3. 条件、例外、否定和单位是否完整？
4. 表格、流程、列表是否保持原含义和依赖？
5. 能否定位到真实原文，而不是只有生成摘要？
6. 是否超出实际模型输入预算，发生截断或信息丢失？

任何改变事实含义的问题均为阻塞项，必须修复并重测。普通排版缺陷记录后修正。解析成功但内容为空、只有标题、引用无来源、切片被截断都不得通过。

## 7. 阶段 E：用真实问题验收检索

初始题集最低设计为60题；当前已有70题，执行第0.4节，保留70题完整回归并增加新的独立留出测试，不能缩回60题。覆盖要求仍为五领域各至少10题、跨领域至少10题；每领域应覆盖概念、条件/例外、流程、案例/表格，以及资料不覆盖或范围不匹配问题。不存在相应内容时如实列为覆盖缺口，不编造答案。

测试题必须先依据原文确定预期，再运行检索。问题改写措辞，避免全部照抄标题；留出一部分题目只用于最终复测，不在每次调参时反复使用。

`retrieval-tests.md` 使用以下字段：

`test_id、领域、问题、是否有可用证据、预期 doc_id/知识点/来源范围、所选知识库、检索参数、Top5 实际证据、是否命中全部必要证据、回答是否保留条件、引用是否定位正确、失败原因`。

建议初始门槛：

| 项目 | 计算和通过条件 |
| --- | --- |
| 可回答题证据命中 | 前 5 条检索结果含所有必要证据的题数 ÷ 有证据题数，目标至少 90%，并分别报告每领域结果 |
| 跨领域问题 | 单独报告；需要两个领域的证据时不能只命中一边就算完整 |
| 无证据题 | 明确说明资料不足或适用范围不匹配；不编造结论和引用，全部通过 |
| 引用准确性 | 测试回答中的实际引用逐项回原文核对，全部可定位且支持对应结论 |
| 关键语义 | 抽检与测试中发现的条件、例外、否定、数值失真必须全部修复 |

如果真实环境不能设置 Top5 或只能返回其他数量，记录实际 k 值并报告对应指标，不冒称测得 Top5。检索结果和最终回答质量分开计算，不能用模型自行补答掩盖检索没有证据。

失败时只按原因修复：没资料→回指导书一；分错库/未选目标库→回指导书二；标题或切片错→回结构与试切；证据已命中但回答错→记录回答生成问题；权限或索引未完成→解决状态问题。不要发现不命中就无差别调大切片长度。
