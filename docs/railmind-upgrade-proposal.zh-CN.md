## 0. 以后怎样直接使用这份文件

如果你只是想让 AI 开始干活，不必每次从头读完。按下面的顺序操作：

1. 第一次，让 AI 执行 [R01-A 现状核对](#task-r01)，确认今天的代码、环境和合并状态。
2. 阅读 [任务顺序表](#execution-order)，选一个本次目标。优先从 R02 或 R03 开始，前提是相关路径已具备修改和验证条件。
3. 复制 [通用任务提示词](#ai-start-prompt)，把任务编号填进去；再附上对应任务卡的专用提示词。
4. AI 结束后，按该任务卡的验收清单检查，再使用 [验收提示词](#ai-review-prompt)复核。
5. 把结果记录到 [任务台账模板](#task-ledger)。下次把台账和本次目标一起交给 AI。

**一次处理一个任务或一个明确子阶段。** 不建议只说“按这个文档把整个项目优化完”，因为它会把交互、数据库、资料迁移和性能改造混到同一轮里，难以确认哪项真正完成。

| 你现在的需求 | 直接阅读 |
| --- | --- |
| 不知道先优化什么 | 第 1 章、[第 15.2 节](#execution-order) |
| 想复制一段话交给 AI | [第 15.3 节](#ai-start-prompt)及对应任务卡 |
| 想知道一个功能到底改哪些地方 | [第 16 章的 R01～R14](#task-cards) |
| AI 说“已完成”，但你不知道怎么检查 | [第 17 章](#verification-guide) |

| 想记录长期进度 | [第 19 章](#task-ledger) |

## 1. 核心判断：下一阶段应围绕“用户能独立完成任务”建设

项目已经有铁路工作台、四类场景、设备背景填写、公开资料导入、Go 检索与问答、来源引用和资料管理。继续推进的主要空间，在于把这些能力组织成清楚、可靠、可以验证的使用流程。

你觉得自己“不会用”，有一部分可以从产品里解释：模型实例、默认模型、文档上传、解析、知识库绑定、助手和会话分散在不同页面；创建问答还有两条行为不同的入口。使用者需要自己拼出这些环节，容易把配置或资料问题误认为模型不聪明。

建议下一阶段确立一个主目标：

> 一名第一次使用的同学，在服务和模型已准备好的情况下，能够不依赖开发者口头指导，完成一次铁路资料查询，找到支持答案的原文，并知道资料不足时下一步该做什么。

围绕这一目标，优先顺序建议为：**稳定当前版本 → 统一问答入口 → 完善首次引导 → 提升资料和引用质量 → 建立评测反馈 → 扩展设备案例与培训任务。**

本建议书不把增加页面数量作为主要成果，也不要求立即重写底层 RAGFlow。

## 3. 当前已经具备的基础

| 能力 | 当前依据 | 使用边界 |
| --- | --- | --- |
| 铁路业务入口 | 工作台提供安全规章、客运服务、设备分析、学习培训 | 场景切换不会自动增加对应资料 |
| 设备背景采集 | 型号、报警信息、位置、时间四个字段 | 目前拼入聊天问题，尚非独立案例或工单对象 |
| 公开资料导入 | 6 份存档、来源清单、SHA-256 校验、上传及解析请求 | 是随项目打包的存档，不是实时法规更新服务 |
| 解析状态展示 | 区分排队、运行、完成、失败、取消等状态 | 就绪只表明有完成文档和片段，不证明检索正确 |
| 知识库和检索测试 | 文件管理、解析结果、参数测试、元数据过滤 | 专业资料质量和适用范围仍需人工整理 |
| 铁路请求规则 | Go 端对铁路标记助手固定提示、引用和空证据回复，过滤部分调用选项 | 提示与分流规则不能单独证明所有回答符合要求 |
| 聊天记录及反馈 | 会话列表、消息、引用查看、回答反馈 | 反馈到知识修正和回归评测的业务流程还需组织 |
| 扩展平台能力 | 工作流、数据处理流程、知识成果、数据源等代码和入口 | 对新用户增加了学习成本，不能默认全部功能已实测可用 |
| 评测起点 | `evaluation.json` 已有 12 道题及预期行为 | 文件没有当前实测成绩，不等于已经完成评估 |
| Go 服务主路径 | API、Admin、ingestor、syncer，前端固定 Go 代理 | 仓库仍有 Python 目录、资源准备脚本与待收敛路径 |

这里最值得继续积累的资产是：有来源的铁路资料、可重复的评测题、可以回查的回答和真实使用反馈。

## 4. 优先处理的具体问题

### 4.1 P0：先建立一个可复现的运行版本

**观察：** 当前还有未合并路径，影响范围包括聊天、模型服务、布局、知识库和问答页面。Compose 使用本地定制镜像标签 `ragflow:railmind-v1.0.0`；仅凭源码和标签不能证明运行镜像含有相同改动。

**影响：** 开发者看到的源码、用户看到的页面、后端实际执行的行为可能不属于同一版本。后续写教程或评测时难以复现。

**建议：** 完成现有合并，确定一个可运行基线，为源码提交、前端产物、Go 二进制和镜像记录相同版本标识。先在独立验证环境确认数据库迁移和主流程，再更新演示环境。

**验收：** 无未合并路径；有明确的代码与镜像对应记录；实际走通“登录 → 配置模型 → 导入 → 解析 → 检索 → 问答 → 查看引用”。保留运行日志和版本信息。

### 4.2 P0：统一两个“新建铁路问答”入口

**观察：** 工作台调用 `createRailwayChat`，带知识库、`domain: railway` 和场景；列表页 `useCreateChatDialog` 使用通用初始配置，知识库为空，没有铁路领域标记。Go 的 `isRailwayChat` 根据标记识别模式，不根据助手名称识别。

**影响：** 用户看到“铁路问答”文字，却可能得到不同的知识绑定和请求规则；给助手改名也无法解决这个差异。

**建议：** 两个入口收敛到同一条创建流程和服务端约束。第一版直接让列表页的新建按钮进入工作台的创建区域，复用已有场景、资料范围与模型选择，删除重复弹窗路径。对既有通用助手显示真实类型；如需要转成铁路助手，通过单独定义的显式迁移与配置检查完成。

**验收：** 两个入口创建同样配置时，后端保存的领域、场景、知识库和模型一致；删除或失效的知识库不能静默产生无资料的铁路助手；名称中的“铁路”不被当作策略依据。

### 4.3 P0：让设置界面与后端实际行为一致

**观察：** 当前聊天设置仍展示通用系统提示、引用和联网配置。铁路请求处理会重新设置系统提示、强制引用和空证据回复，并将联网选项置为关闭。

**影响：** 用户保存了设置却看不到预期变化，容易认为系统失灵。已有项目说明中的“界面隐藏相应开关”也与当前文件状态不一致。

**建议：** 铁路模式只显示实际可调整的项；固定规则以简短说明展示。对于仍支持的推理方式，应逐条验证后端分流，明确资料范围和引用约束，不用单个开关名称代替能力说明。

**验收：** 所有可编辑字段都有可解释的效果；固定项不能制造“保存成功但不生效”的体验；普通检索与智能检索模式分别完成真实证据与越权测试。

### 4.4 P1：把首次使用做成可见的任务进度

**观察：** 工作台准备区默认折叠；“模型已就绪”主要依据模型 ID；资料就绪依据状态和片段数。首页“开始对话”只预填问题，仍需在聊天页发送。

**影响：** 用户不清楚哪个步骤未完成，也可能把进入聊天页误认为已发送问题。

**建议：** 首次进入时展示四项准备进度：模型连接验证、资料导入、解析完成、第一条检索命中。每项只给一个明确下一步；完成后缩成状态条。第一版明确保留“进入聊天页检查后再发送”，将按钮和说明改为能表达这一行为的文字；自动发送作为另一个需要防重复机制的任务，当前不一起做。

**验收：** 5 名未参与开发的试用者，在模型已可用条件下至少 4 人能独立完成第一问；能说清楚输入的消息是否已发送。记录卡住的位置和完成时间，不能只用开发者自测代替。

### 4.5 P1：减少重复助手与状态轮询开销

**观察：** 工作台每次发起会创建带随机标识的新助手；知识库列表约每 10 秒轮询，选中库的文档约每 5 秒轮询，文档接口逐页获取完整列表。

**影响：** 日常反复提问会让助手列表变杂；资料增多后，全量轮询可能带来额外请求和传输。后者是由实现推导的扩展风险，本次没有测量负载或证明已经形成瓶颈。

**建议：** 区分“新助手”和“新会话”；从已有助手继续使用时不再创建配置对象。状态展示优先查询聚合统计和活动任务，仅在有运行任务或用户关注页面时轮询，数据量增大后再评估事件推送。

**验收：** 连续使用同一个已有助手提问 10 次不会生成额外助手；无活动任务时停止短周期全量轮询；在 100、1000 份文档样本下记录请求次数、响应体积和状态更新延迟。助手复用属于 R05，轮询优化属于 R13，分开实施和验收。

### 4.6 P1：把资料版本管理从说明文字变成日常操作

**观察：** 清单有来源、采集时间和哈希；导入按文件名去重。同名存档正文更新后，重复导入不会自动替换库内旧文件。六份资料主要覆盖规章和监督要求。

**影响：** 用户可能以为“重新导入”就是更新资料；设备类回答缺少适用手册时，提示词再详细也补不上事实依据。

**建议：** 新增资料修订流程，记录内容哈希、来源、版本、适用对象、审核状态和替代关系。发现内容变化时给出待审修订，审核后发布并重新索引。旧版从活动检索中退出，按审计需要归档；不要长期保留重复活动数据或两套处理实现。

**验收：** 同一来源有新版本时能显示差异与状态；当前回答可追溯到确切文档版本；旧版是否参与查询有明确规则；具备一套型号清楚、范围可控的设备教学资料。

### 4.7 P1：补上固定题集与真实反馈的改进循环

**观察：** 仓库已有 12 道评测题，覆盖有依据查询、资料不足、版本、危险请求和提示注入；界面已有回答反馈。

**影响：** 如果只看展示效果或偶尔问几题，无法判断换模型、改分块和改提示究竟改善了什么。

**建议：** 先运行现有题集，记录原始结果，再扩大到分场景的 60 道题。每次改动使用固定题目比较，新增真实失败问题作为回归题。现有赞踩入口用于收集反馈，后续补上问题分类、处理状态和复测记录。

**补充核对：** `internal/service/chat_session.go` 已有片段反馈加权实现，受 `CHUNK_FEEDBACK_ENABLED` 等配置控制。新增的“问题处理状态”与已有“赞踩影响检索权重”是两件事，不能在新增管理流程中再次触发同一次投票的加减权重。

**验收：** 每次评估都能找到问题、资料版本、模型、参数、检索结果、回答和人工评分；每条已解决反馈都有修复后复测记录。

### 4.8 P1：同步当前说明、菜单与实际能力

**观察：** `docs/railway-agent.md` 记载删除通用创建、移除 Agent 入口、手机设置抽屉及禁止某些研究路径；当前代码恢复了列表创建和“更多”，聊天设置仍是固定宽度面板，推理选项也进入了新分流逻辑。这里确认的是文件间不一致，不能引用旧测试记录证明现状。

**建议：** 发布版本时同步操作手册、导航和能力清单。历史验证保留日期和版本，失效的现状描述直接删除或改写。移动端重新验证聊天设置面板、输入区域和会话切换，不沿用旧截图结论。

**验收：** 新用户按手册能找到每个必要按钮；未上线能力不会出现在“已实现”清单中；当前手机和桌面视口有本版本的检查记录。

### 4.9 执行前必须复用的两项已有能力

解析进度已有 `GET /api/v1/datasets/:dataset_id/ingestions/summary`，处理链经过 `internal/handler/dataset.go` 和 `internal/service/dataset/ingestion.go`。优化首页状态时先看它的实际字段、权限和统计口径，再决定是否需要扩展；不要先新建一个功能相同的状态接口。

聊天反馈已有消息存储和可选片段加权路径。新增质量问题分类、人工处理和复测记录时，先确认现有字段是否足够，避免与已有反馈数据分离。

## 5. 下一版产品怎样组织

### 5.1 首页只承担三项任务

1. 告诉用户当前是否具备问答条件，缺什么。
2. 帮助用户选择场景与资料范围，描述问题。
3. 提供最近使用的助手和最近任务，便于继续。

现有官方资料展示可以保留，但主要操作和首次引导应出现在用户容易看到的位置。滚动动画和装饰应服从输入、阅读和低配置设备的流畅度。

### 5.2 分清三类角色的任务

| 使用角色 | 主要任务 | 优先提供的能力 |
| --- | --- | --- |
| 学习者 / 查询者 | 提问、读依据、记录疑问 | 场景示例、引用查看、继续会话、具体反馈 |
| 资料维护者 | 导入、检查、更新资料 | 解析异常、版本状态、适用范围、重复资料处理 |
| 系统维护者 | 配置模型、排查服务、备份和发布 | 模型验证、任务诊断、版本信息、运行指标 |

这是一种交互分工建议，不代表当前开源版本已经提供这些完整角色权限。涉及权限时应使用真实的服务端授权；不能仅靠前端隐藏按钮。企业专属能力继续遵循仓库的 downstream 和 build tag 边界。

### 5.3 回答应帮助用户判断依据

建议按问题复杂度逐步采用以下结构，不强迫简单概念题输出长报告：

- 资料支持的结论。
- 对应的来源片段及版本。
- 未确认的条件与信息缺口。
- 用户下一步可做的资料核对或补充。

设备分析可以进一步区分“用户提供的现象”“资料支持的可能解释”“没有证据的推测”。未来若引入置信展示，应先有校准数据；不要把检索相似度显示成故障概率。

### 5.4 可以真正形成差异的三个业务方向

| 方向 | 可交付的小版本 | 为什么值得做 |
| --- | --- | --- |
| 有版本依据的规章学习 | 按资料整理提纲、对比职责、生成可核对的练习 | 现有资料较适合，容易先验证价值 |
| 一个型号的设备案例辅助 | 输入现象，检索适用手册与脱敏案例，列出信息缺口 | 专业深度取决于资料与专家复核，可形成可解释的专题能力 |
| 从错误到改进的质量记录 | 提交错误，定位资料或检索问题，复测并关闭 | 可以证明系统持续改善，而不仅是一次展示 |

建议先选择一个设备类型和一个使用场景做深，避免同时覆盖信号、车辆、供电、轨道等全部领域。

## 6. 数据与知识建设方案

### 6.1 建议的最小资料台账

先利用已有元数据能力验证这些字段，确实需要跨文档审核时再扩展 Go 数据模型。

| 字段 | 用途 |
| --- | --- |
| 文档标识、标题、来源地址 | 定位与追溯 |
| 内容哈希、修订号、采集日期 | 判断重复和内容变化 |
| 发布与生效信息、状态 | 区分文档时间和业务适用性；未知时明确未知 |
| 设备类型、型号、适用场景 | 限定检索范围 |
| 审核人、审核时间 | 明确资料责任 |
| 访问范围 | 避免不应共享的资料进入他人检索 |
| 替代版本关系 | 支持版本变更和原答案追溯 |

不要让模型凭文本自动决定规章是否现行有效；自动提取可以生成待审核字段，最终状态由有责任的资料维护人员确认。

### 6.2 文档处理顺序

```text
收集合法资料 → 核对来源与范围 → 清理文档 → 解析抽查
    → 建立片段与索引 → 固定问题检索测试 → 发布给助手使用
```

按样本逐步验证通用文字、PDF、扫描件、表格。优先检查条款编号、否定词、数值与单位、跨页表格的对应关系。解析正确之后再比较分块长度和重排序效果。

### 6.3 设备案例应保存什么

未来设备案例对象至少区分：案例来源、设备型号、现象、报警代码、发生条件、已核实原因、证据材料、人工结论和脱敏状态。AI 的推测不得自动写入“已核实原因”。

初期可先以标准化 Markdown 案例导入，证明检索有用之后再做独立案例管理页面。这样可以先验证资料价值，避免先做复杂表单却没有可用案例。

## 7. 建立可执行的评测方法

### 7.1 从已有 12 题开始

使用 [现有评测文件](../web/public/railway/evaluation.json)，先由专业教师或熟悉资料的人核对题目预期和资料适用性。运行后保存原始结果，包括拒答和失败，不能只展示成功回答。

第二阶段扩充到 60 题，以下是建议构成，不是当前已存在题量：

| 类别 | 建议题量 | 关注点 |
| --- | ---: | --- |
| 有明确资料依据的直接问题 | 20 | 能否找到和正确解释原文 |
| 跨段落或跨文档比较 | 10 | 是否合并错条件、漏引用 |
| 无答案或资料不完整 | 10 | 是否承认不足、提出有效澄清 |
| 型号、版本与适用范围冲突 | 8 | 是否把不同对象混用 |
| 不当操作、伪造依据与注入请求 | 8 | 是否保持证据与权限边界 |
| 口语、错别字和追问 | 4 | 是否保留意图与上下文 |

扩充题集时保留一部分不用于日常调参的题目，防止只针对已知题目优化。

### 7.2 每次评估保存的内容

```text
评估编号 / 日期 / 代码版本 / 镜像版本
问题编号 / 场景 / 是否可由当前资料回答
知识库及文档版本 / 对话模型 / 嵌入模型 / 重排序模型
检索和生成参数 / 返回片段及排名
回答原文 / 引用对应关系
首段响应时间 / 总耗时 / 错误和重试
人工评分 / 评分理由 / 复核人员 / 后续问题编号
```

### 7.3 指标定义与建议门槛

下面的门槛是小规模教学或试用版本的规划目标，**不是现测成绩，也不是铁路生产安全标准**。先采集基线，再与评审人员确认是否调整。

| 指标 | 计算方法 | 建议试用目标 |
| --- | --- | --- |
| 首次流程完成率 | 无开发者口头提示完成首次有引用问答的人数 / 试用人数 | 5 人中至少 4 人 |
| 检索命中率 Hit@5 | 在前 5 个结果中找到至少一个正确证据的问题数 / 可回答问题数 | ≥ 85%，同时报告样本量 |
| 引用支持率 | 被引用原文实际支持的关键断言数 / 有引用的关键断言数 | ≥ 95% |
| 引用覆盖率 | 附有效证据的关键事实断言数 / 应提供证据的关键事实断言数 | ≥ 90% |
| 无依据处理通过率 | 无答案题中正确说明不足且未编造事实的题数 / 无答案题数 | ≥ 90% |
| 不当操作与伪造依据用例 | 已定义测试集中的失败数 | 目标 0；任何失败都登记并阻断相关场景试用 |
| 文档处理成功率 | 成功得到可检索片段的有效输入文档数 / 有效输入文档数 | 固定小样本目标 ≥ 95% |
| 性能 | 分别统计首段响应和完整回答的 p50、p95 | 先按固定硬件、模型、并发测基线，再定数值 |

单独报告分母、样本量和失败样例。小样本里“0 次失败”只说明这组测试未观察到失败，不能宣传成所有输入都安全。

### 7.4 三组对照实验

在隔离评测环境中比较：

1. 相同对话模型的直接问答。
2. 相同资料、模型与检索配置的普通 RAG。
3. 增加铁路场景、信息澄清和证据规则的当前方案。

保持资料版本和参数可比；涉及不同模型时，把模型变化单独作为变量。结果由人工核对引用与断言，不只让模型给另一个模型打分。

普通 RAG 和直接问答作为评测对照，不需要重新在面向用户的铁路产品里维护多套创建路径。

### 7.5 反馈处理流程

```text
用户标记问题 → 归类到资料/解析/检索/生成/交互
    → 复现 → 修复 → 加入回归题 → 复测 → 记录处理结果
```

优先补齐现有反馈的可追踪处理过程，不另起一套互不关联的反馈系统。

## 8. 技术升级建议

### 8.1 前端：先解决任务路径和状态表达

- 统一助手创建，明确“助手”和“会话”的区别。
- 让模型验证、上传、排队、解析、检索、生成的状态各自可见。
- 关键错误给出可执行下一步，例如“去配置 Embedding”，而不是只显示请求失败。
- 对话规则固定时，隐藏无效的编辑项并解释原因。
- 调整手机聊天设置面板和表单布局，验证 320、390 像素及桌面宽度。
- 动效支持减少运动偏好，页面切换和滚动不妨碍阅读；实施前测量现状。

### 8.2 Go 后端：让业务约束归属明确

铁路领域策略集中在现有服务层的拥有者附近；创建约束、请求策略和证据要求应被实际入口一致调用。避免仅靠前端传入标记来保证整个产品的行为。

重点验证：新建和更新助手、普通检索、智能检索、分享访问、API 访问、知识库权限变化、资料删除、无检索结果和模型失败。这里列的是后续验收路径，不表示本次已经证明它们有漏洞。

来源应保留文档及片段标识和可追踪版本。未来的案例、资料审核与评测记录由明确的 Go 服务负责，不把业务规则散布到页面与提示词中。

### 8.3 性能：先测量再投入

分别记录上传到解析完成、检索、重排序、首段生成、完整生成的耗时。对常见故障区分“队列等待”“模型限流”“文档解析慢”“检索慢”。

初期优先做活动任务查询、合理分页、终止无意义轮询和服务商调用限流。没有基线前，不建议因为感觉慢就更换整个检索引擎或引入复杂集群。

成本比较应记录真实请求次数、输入输出量和服务商账单或本地资源消耗。文档更新需要重算索引时，也应计入导入成本。

### 8.4 数据与权限：落实到每条读写路径

资料上传、检索、来源预览、分享和下载都需要真实服务端权限检查。对于文档内的指令文本，应当作待检索内容，不作为授权或工具执行命令。

建议在已有铁路规则之外做输入与输出检查、工具最小权限、审计与必要的人工确认，并用固定测试验证。提示词不能承担全部防护责任。这与 OWASP 的分层防护思路一致。[OWASP 提示注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

### 8.5 部署与恢复：保证可复现

固定应用和依赖版本，输出实际构建信息；启动诊断同时覆盖 API、任务处理、对象存储、检索和模型可达性。演示环境与测试环境区分，升级前在测试环境做恢复和回归。

业务数据库、原始资料、索引、模型配置和密钥存放方案应形成备份清单。数据库使用适合其一致性要求的备份方式；不能因为 Docker 卷可以打包，就认定运行中的多服务数据天然一致。[Docker 数据卷与备份说明](https://docs.docker.com/engine/storage/volumes/)

恢复验收要从备份恢复一个知识库和一个助手，并重新检索出已知片段。不要仅验证容器能够启动。

### 8.6 Go-only 收敛作为独立工程事项推进

遵循现有 AGENTS 指引，按以下依赖顺序处理：

1. 盘点仍需保留的行为，确认 Go 或前端已有真实实现和测试。
2. 先替换 native 静态库、模型和 BPE 下载的 Python 准备脚本。
3. 按仓库约束迁移 DeepDoc 资源位置，同步发现逻辑、依赖准备、Docker 打包与测试。
4. 删除不再使用的 Python 服务、SDK、测试、依赖、容器和 CI 路径。
5. 清理迁移完成后的旧说明、重复实现和无用公开接口。

新业务继续写在 Go 和前端。整体移除完成前，不为了赶进度保留新的 Python 回退；也不把“先删目录”当成迁移完成。

这一工程事项规模取决于剩余依赖，不应未经盘点就承诺在一周内完成。用户流程优化与现有 Go 路径可以先完成，移除工作按独立验收推进。

## 9. 六周实施路线

假设：一名熟悉当前仓库的全栈开发者，一名可定期参与的资料或专业评审人员，已有能运行基础服务的环境。下列人日是初步估算，不包括大规模原始资料整理、服务商采购或完整 Python 移除。

| 阶段 | 主要交付 | 估算开发人日 | 退出条件 |
| --- | --- | ---: | --- |
| 第 1 周：稳定基线 | 完成合并、版本对应、运行自检；记录改前基线，再统一创建入口 | 3～5 | 真链路可复现，创建语义一致 |
| 第 2 周：首次使用 | 四步引导、设置一致性、错误指引、助手与会话区分 | 3～5 | 新用户完成首次任务，记录可用性结果 |
| 第 3 周：资料质量 | 文档台账、一个设备专题资料包、解析抽查、更新规则 | 3～5 | 资料可追溯，专题问题能检索到原文 |
| 第 4 周：评测与反馈 | 基线复测、扩充题集、结果记录、反馈分类与回归 | 3～5 | 能展示修复前后的真实差异 |
| 第 5 周：专题体验 | 一个设备案例流程或一个培训任务模板 | 3～5 | 专业评审确认适用范围和证据质量 |
| 第 6 周：发布准备 | 性能基线、移动端检查、恢复演练、同步手册与演示 | 3～5 | 可重复演示、可恢复、能力清单准确 |

总量约 18～30 个开发人日，评审和资料准备另外计时。遇到基础依赖、合并或原生库阻塞时，以退出条件重排计划，不按日历强行宣布阶段完成。

上述估算对应轻量试用版本。第 16 章中 R06-B 的完整发布与历史追溯、R09-B 的处理流程，以及 R14 全量移除，应在盘点后另外估算；不能把扩写后的全部任务卡都理解成六周内必须完成的承诺。

### 9.1 如果目前只有一个人、时间也有限

先做一个两周最小交付：稳定基线、统一入口、首次引导、跑完现有 12 题、完善手册。设备案例库、成绩系统、知识图谱专项优化、外部渠道都暂缓。

### 9.2 本周可以立即开始的五件事

1. 保存当前合并状态信息，完成一个可构建、可启动的确定版本。
2. 按配套说明亲自完成一次首次问答，记录每个卡点。
3. 在改变问答行为前，用现有 12 道题记录第一次结果，标注“未测”“失败”和“通过”。
4. 把两个创建入口统一到真实铁路配置流程。
5. 找两名没参与开发的人试用，只观察他们操作，记录卡住的位置。

### 10.1 测试要求

修改哪个行为就先运行最小相关检查。Go 测试通过 `build.sh`，需要真实外部服务的用例使用 integration、e2e 或 manual 标签；不能把实际模型测试混进默认无服务单元测试。

```bash
bash build.sh --test ./internal/service/...
bash build.sh --test ./internal/handler/...
```

以上分别用于涉及的服务或处理器变更，不表示每次文档变更都要运行。跨组件上传到问答使用真实依赖完成端到端验证；手动昂贵测试不纳入 CI。构建后按改变的服务模式执行帮助命令并验证启动环境，关注实际 Linux 链接器。

前端先跑修改范围的格式、Lint、相关测试和类型检查；页面交互还要用真实浏览器验证。已有全仓错误要记录基线，不能用“本来就有错误”掩盖新问题。

文档中的建议验收未在本次执行；这次仅新增和核对说明材料。

## 11. 哪些事可以暂缓

| 暂缓项 | 原因 | 重新考虑的条件 |
| --- | --- | --- |
| 不断更换首页视觉主题 | 对首次问答成功和引用质量收益有限 | 已确认存在阅读或可用性问题 |
| 同时接入很多模型服务商 | 配置和排错成本增加 | 明确存在质量、成本或部署要求 |
| 一开始就训练铁路大模型 | 目前主要缺口仍是资料、检索、流程和评测 | 已有足量合法数据及可靠基线，能证明必要性 |
| 大规模复杂工作流 | 增加调用链和诊断难度 | 单次检索问答无法完成明确业务任务 |
| 把图谱或 Wiki 当成必备展示 | 有图不代表证据正确或任务完成 | 用户有具体跨实体检索需求且效果可验证 |
| 同时覆盖所有铁路专业 | 资料和评审资源分散 | 一个专题已形成稳定方法和数据流程 |
| 自动执行现场操作 | 超出当前知识辅助定位和验证能力 | 另立有明确责任、权限和行业验证的项目 |

## 12. 如果用于课程、竞赛或毕业设计

现有项目说明提到了教学和参赛用途，因此可以把成果组织为以下四部分：

1. **业务问题**：资料分散、难查依据、型号和版本容易混用。
2. **具体实现**：铁路场景入口、设备背景、资料溯源、统一的证据规则与任务引导。
3. **实验依据**：固定题集、三组对照、引用核查、无依据处理、响应时间和用户试用记录。
4. **局限与下一步**：资料范围、版本复核、未覆盖型号、真实使用反馈。

明确标注 RAGFlow 作为开源基础；自研贡献按实际修改和实验说明。不要将平台原有解析、向量检索、工作流和通用引用能力全部归为独立原创。

答辩演示优先展示“能查到依据的一题、会说明资料不足的一题、一次可追踪的错误修复”。这比只展示连续流畅回答更容易说明项目价值。

## 13. 建议的阶段完成标准

下一版达到以下状态即可形成一个可评审的交付：

- 当前版本可构建、可启动，代码与镜像对应。
- 主创建入口一致，用户能区分助手与会话。
- 新用户能按说明完成首次有引用问答。
- 六份内置资料及至少一个自有专题资料集经过范围核对和解析抽查。
- 现有题集有真实结果，主要失败有明确归因。
- 引用能回查，资料不足不会被当作必须生成确定结论的错误。
- 至少完成一次用户反馈到修复复测的循环。
- 桌面和手机关键流程有本版本验证记录。
- 完成一次备份恢复验证，手册和能力清单与发布版本一致。

达标后，再根据实际使用频率选择设备案例或培训任务继续建设。

- [ ] 开源构建通过；涉及 enterprise 接缝时记录下游验证条件，未取得下游环境不宣称其已通过。

**专用提示词：**

```text
本次只执行 R14-A，盘点受支持构建和运行路径中的 Python 依赖。
从真实调用方、下载脚本、资源发现、Docker、CI 和测试反向核对。
每项列出：使用方、是否仍需、Go/前端替代情况、删除前验证、风险与下一阶段。
注意两个下载脚本可能有重叠，不照旧文档硬分工。
本轮不删除目录、不迁移数据、不实现完整 Go-only 改造。
输出可据此单独执行 R14-B 的清单与验收输入。
```

## 17. 怎样验收 AI 的优化结果

### 17.1 四层验证分别证明什么

| 层次 | 典型检查 | 能证明什么 | 不能据此声称什么 |
| --- | --- | --- | --- |
| 代码与静态检查 | 实际调用链、Lint、类型检查、构建 | 基本结构、语法和部分约束符合要求 | 用户点击一定成功，模型答案一定正确 |
| 定向自动测试 | Go 单元测试、前端逻辑和交互测试 | 定义的边界和回归场景符合预期 | 模拟服务等同于真实系统 |
| 真实链路 | 真实上传、任务服务、索引、模型、浏览器 | 指定环境和数据下完整路径可用 | 所有设备型号或所有问题都可用 |
| 用户与专业验收 | 新用户操作、引用核查、教师复核 | 任务可完成、答案适用性得到具体核查 | 小样本结果等同于全行业保证 |

对创建、策略、数据发布等核心行为，测试不应只确认页面有几个文本或对象含某字段，而应覆盖真实错误与状态转换。对简单文案或可逆低影响调整，不必硬加一堆只复述实现的测试。

### 17.2 可复用的命令示例

下面是供后续任务选择的示例，**不是本次已运行记录，也不是每项任务都必须全部执行**。AI 应先确认当时的路径、脚本和测试名称。

在项目支持的 Bash 环境中，从仓库根目录运行 Go 检查：

```bash
# 铁路策略相关现有测试；修改其他包时改成实际拥有者。
bash build.sh --test -run 'TestPrepareRailway|TestRailway' ./internal/service

# 数据集或文档行为改变时，先选实际涉及的包。
bash build.sh --test ./internal/service/dataset/...
bash build.sh --test ./internal/service/document/...

# 只有相关真实服务已准备好且任务需要时才运行相应层次。
bash build.sh --test-integration ./internal/service/dataset/...
```

不能把“没有匹配到测试”视为行为验证通过。命令过滤的测试名与执行数量要写入结果。集成或端到端验证应确认没有被环境 guard 全部跳过。

在 `web` 目录运行前端相关检查，示例只针对工作台和铁路服务：

```powershell
# 根据实际修改文件调整列表；仅在已安装对应项目依赖时运行。
npx --no-install oxfmt --check src/services/railway-service.ts src/pages/home/use-railway-workbench.ts
npx --no-install oxlint src/services/railway-service.ts src/pages/home/use-railway-workbench.ts
npm run test -- --runInBand --coverage=false --runTestsByPath src/services/railway-service.test.ts src/pages/home/use-railway-workbench.test.tsx

# 当改动或项目检查要求需要时执行。
npm run type-check
npm run build
```

格式不通过时，对实际修改文件运行 formatter 后再检查。前端提交前的要求以当时 `web/AGENTS.md` 为准。全仓检查若有历史失败，记录具体诊断与本轮关系；不能仅写“都是原有问题”。

原生构建失败时，先检查 `build.sh` 和 `internal/development.md` 中的依赖与链接器要求。不要通过禁用正常功能、删除失败测试或改回 Python 服务来让命令变绿。

### 17.3 要求 AI 使用的交付报告格式

```text
任务：Rxx / 子阶段
当前状态：已实现待验证 / 已验证完成 / 有阻塞等

1. 原问题是否仍存在
   当前代码证据、复现条件；若已修复，说明本轮实际补齐什么。

2. 本轮行为变化
   用“用户原来怎样操作、现在会发生什么”解释。

3. 修改范围
   文件、拥有的行为、必要的数据或接口变化。
   删除了哪些被替代路径，是否还有真实外部依赖。

4. 验证证据
   命令、执行目录、实际结果、用例数量、是否跳过。
   浏览器操作与真实服务验证分别记录。

5. 验收清单逐项结果
   通过 / 失败 / 未执行，并说明原因。

6. 尚未完成的事
   环境、资料、人工复核或实现缺口；不要混在“已完成”里。

7. 用户怎样亲自检查
   三到六步操作，写清预期可见结果。

8. 版本与后续
   当前源码状态、相关产物、台账位置、下一个合适任务。
   涉及状态或数据变更时写明恢复方法及其限制。
```

报告不必很长，但必须具体。`测试通过`、`功能正常`、`已优化性能`这类单独结论不能替代证据。

<a id="ai-review-prompt"></a>

### 17.4 AI 完成后，可直接复制的复核提示词

```text
请按 docs/railmind-upgrade-proposal.zh-CN.md 的任务 [Rxx] 做一次完成度复核。
独立检查当前代码和本轮修改，不直接采信上一条“已完成”的说明。

逐项核对：
1. 任务卡目标、范围和每项验收条件是否满足；
2. 是否保留了被替代的重复路径，是否误伤真实共享调用者；
3. 正常、失败、重试、刷新、账号或权限变化是否覆盖；
4. 测试真正运行了什么，是否有跳过或仅用了模拟接口；
5. 说明书与当前页面、后端规则是否一致。

在原任务授权范围内修复可确认的问题并运行最窄相关检查。
新增需求只记入台账，不自动展开到其他任务。
最后给出通过、待验证、未完成的逐项结论和证据，不伪造用户或专业验收。
```

### 17.5 你本人最少检查这六件事

即使不熟悉代码，也可以做以下检查：

1. 让 AI 指出修改后的入口，按它给的操作亲自点一遍。
2. 用一个正常输入，再用一个明显缺资料或缺配置的输入。
3. 刷新页面，检查保存的配置和记录是否还在。
4. 如果涉及多个助手或会话，切换后看是否串消息、串引用。
5. 如果涉及回答，打开引用，核对原文是否支持关键句。
6. 查看台账中哪些测试没做，是否把“待验证”写成了完成。

业务准确性不确定时，把具体问题、回答和引用交给专业人员；不要只转述“AI 说答案是对的”。

## 18. 出错、暂停或换一个 AI 时怎样继续

### 18.1 遇到失败先归类

| 类型 | 例子 | 应怎样处理 |
| --- | --- | --- |
| 环境问题 | Docker 未启动、缺原生库、模型权限不可用 | 记录缺失条件，修复环境或继续不依赖它的工作；不改业务逻辑掩盖 |
| 原有代码问题 | 修改前已存在的同一类型检查错误 | 保留基线、确认与本轮关系；仅在阻塞当前目标且范围合理时处理 |
| 本轮引入问题 | 原能工作，改后保存失败或引用丢失 | 优先定位和修复，重跑相关回归 |
| 资料问题 | 缺手册、错误扫描件、版本未知 | 修正资料或缩小业务范围，不强迫模型编答案 |
| 未明确的业务规则 | 两个版本哪个允许发布、谁能查看资料 | 列出需要的人类判断；独立实现可继续 |
| 文档落后于代码 | 路径搬迁、功能已修复 | 更新证据和任务范围，不照旧路径重建一套 |

### 18.2 定向修复失败的提示词

```text
继续处理 [Rxx]。当前失败是：[粘贴关键错误，删除密钥和无关敏感信息]。
先判断它属于环境、原有问题、本轮问题还是资料问题，并给出证据。
检查完整相关调用链，修复实际原因；不要删除测试、放宽校验或改回旧服务来绕过。
只做与本任务直接相关的修改，完成后重复失败场景及必要回归。
更新台账中的状态，不把暂时无法运行写成已通过。
```

### 18.3 中途停止时应留下什么

至少记录任务与子阶段、已改文件、当前工作树状态、已跑命令和结果、剩余验收、正在运行的进程或容器、临时数据位置。写清哪些是本轮创建，哪些属于用户已有环境。

不要自动删除调试环境或覆盖数据来制造“干净状态”。需要停止或清理时，仅针对本轮已确认的资源执行适当操作。

### 18.4 换一个 AI 聊天的交接提示词

```text
请接手 D:\ragflow 的 [Rxx / 子阶段]。
先读 AGENTS.md、建议书对应任务卡，以及 docs/railmind-optimization-progress.md。
如果台账文件不存在，请读取我下面粘贴的上一轮交付报告，不假定已有记录。

不要从头重新设计，也不要覆盖未提交改动。
先核对台账与当前代码的差异，确认上一轮真正完成了哪些行为和测试。
从未完成项继续，在原任务范围内完成实现和验证。
缺失信息可以从源码、测试或运行状态核实的，先自行核实。

上一轮交付报告：
[粘贴报告]

本轮希望完成：
[填写一个具体剩余项]
```

这里的台账路径是建议新建的路径，不表示本次已经创建该文件。

### 18.5 怎样避免 AI 越改越散

- 任务卡写了阶段 A，就只交付阶段 A；把阶段 B 的新想法记入后续。
- 对每个新增依赖或新服务，要求说明现有能力为什么不能满足目标。
- 对每次删除，确认没有仍需要的调用者，并有替代行为证据。
- 对每个新表或接口，说明数据归属、权限、失败和重试行为。
- 对“重构顺手优化”要求解释它为什么是当前任务必要部分。
- 对没有测量的性能结论，要求补基线或明确写成待验证假设。

常规可逆修复可以在既有任务授权内完成。不要把这些规则用成“每改一行都要你确认”；只有需要新业务决定、关键缺失信息或不可逆操作时才应请求输入。

### 18.6 版本和数据恢复怎样区分

只改前端或服务逻辑时，恢复代码与重新部署可能足够；涉及 schema、资料替换和索引重算时，恢复旧代码不代表数据已经恢复。执行 AI 应在实施前明确：

1. 哪些数据会改变，是否有一致备份或可重建输入。
2. 旧版本是否能读取新状态，不能时如何恢复到一致版本。
3. 外部存储或索引部分失败时如何补偿和重试。
4. 恢复后用哪个具体知识库和问题验证。

在本项目要求下，优先采用有明确终点的一次迁移，不为了模糊的“可能以后要回退”长期保留两套业务实现。

## 19. 长期优化台账模板

### 19.1 台账怎样保存

建议后续第一次真正执行任务时，新建 `docs/railmind-optimization-progress.md`。本次只提供模板，不把未实施任务标为完成。台账和建议书职责不同：建议书定义目标，台账记录真实进度。

| 状态 | 何时使用 |
| --- | --- |
| 未开始 | 尚未进行本任务 |
| 核对中 | 正在确认当前问题、范围和环境 |
| 实施中 | 已在修改，但目标尚未完成 |

| 本期不做 | 主动调整优先级，写明原因 |

“有阻塞”是项目台账中的事实记录，不是把所有独立工作都停下；可继续部分仍应列清楚。

### 19.4 每完成三项任务后做一次小复盘

检查新用户是否更容易完成第一问、正确证据是否更容易找到、原有功能有没有退化、最常见失败是否减少。根据真实反馈调整下一项任务，不机械追求把 14 个编号全部划掉。

建议最先形成的可展示成果是：**一个确定运行版本、一条统一问答路径、一份真实评测记录，以及一个能够独立上手的用户。**
