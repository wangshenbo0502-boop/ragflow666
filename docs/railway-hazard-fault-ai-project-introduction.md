# RAGFlow 项目介绍与铁路危险故障解答 AI 改造方案

## 1. 文档说明

本文档基于当前 RAGFlow 代码仓库、Docker 配置、Go 后端实现和 React 前端实现整理，主要用于以下场景：

- 向老师、指导教师或项目组成员介绍现有 RAGFlow 系统；
- 解释系统的整体架构、工作原理、目录结构和主要技术实现；
- 说明如何在基本不改动后端的前提下，将系统改造成“铁路危险故障解答 AI”；
- 为后续接收铁路规章、设备说明书、维修手册、事故案例等资料后的开发工作提供实施依据；
- 作为课程设计、毕业设计、项目立项或阶段汇报文档的基础材料。

当前仓库同时包含 Go 新架构、React 前端以及部分历史 Python 实现。当前 Docker 配置已经可以使用 Go 服务启动 RAGFlow，但仓库中的 Python 目录、脚本和兼容代码仍然存在。因此，本文对系统现状的描述以“当前可运行实现”为准，对铁路业务改造部分以“建议方案”为准。

本文档只描述系统和开发方案，不修改现有业务代码。

## 2. 项目概述

### 2.1 RAGFlow 是什么

RAGFlow 是一个面向企业知识库和智能问答场景的检索增强生成系统。它将用户上传的文档、网页、表格、图片、扫描件等非结构化或半结构化资料进行解析、清洗、切片、索引和检索，再将检索到的资料作为上下文提供给大语言模型，最终生成带有来源依据的回答。

它不是简单的聊天机器人，而是一个包含以下能力的完整知识应用平台：

1. 文档和数据源管理；
2. 知识库管理；
3. 多种格式文件解析；
4. 文档分块和文本清洗；
5. 关键词检索、向量检索和混合检索；
6. 大语言模型调用；
7. Agent 工作流编排；
8. 对话历史管理；
9. 引用和证据展示；
10. 模型、用户、权限和团队管理；
11. 外部数据源同步；
12. 管理后台和运行监控。

### 2.2 项目解决的问题

普通大语言模型只依赖训练阶段学到的知识，可能存在以下问题：

- 不知道企业内部资料；
- 无法准确回答最新规章和现场制度；
- 容易产生没有依据的回答；
- 无法定位回答来自哪份文件、哪一页或哪一段；
- 不能直接利用用户上传的 PDF、Word、Excel 和图片资料；
- 不能很好地处理长文档、多文档对比和复杂问题。

RAGFlow 通过“先检索，再生成”的方式解决这些问题：

```text
用户问题
   |
   v
问题理解与检索词生成
   |
   v
从知识库检索相关文档片段
   |
   v
筛选、排序、拼接证据
   |
   v
将证据和问题一起提交给大语言模型
   |
   v
生成有依据的答案和引用
```

### 2.3 改造成铁路危险故障解答 AI 的目标

本项目计划在 RAGFlow 的基础上，建设一个面向铁路设备维护、故障判断和安全处置的智能问答系统。

系统的核心目标是：

- 让维修人员或学习人员能够使用自然语言描述铁路设备故障；
- 根据铁路规章、设备说明书、维护手册、故障案例和老师提供的资料进行检索；
- 给出故障现象分析、可能原因、检查步骤、处理建议和安全注意事项；
- 对答案进行资料引用，能够查看答案对应的原文；
- 对危险操作进行安全提醒；
- 对无法确定或资料不足的情况明确提示“需要人工确认”，避免系统武断下结论；
- 尽量只改造前端交互和展示方式，复用 RAGFlow 已有的后端知识库、检索、模型和引用能力。

需要强调：铁路故障解答 AI 属于安全相关场景。系统适合做知识查询、培训辅助、故障分析参考和资料定位，不应直接替代现场作业规程、调度命令、检修负责人判断或铁路行业的正式安全审批流程。

## 4. RAGFlow 的工作原理

## 4.1 文档入库流程

用户将文件上传到知识库后，系统通常经过以下步骤：

```text
上传文件
   |
   v
保存原始文件到对象存储
   |
   v
识别文件类型
   |
   v
选择解析器
   |
   v
提取正文、表格、图片、页码和版面信息
   |
   v
文本清洗与结构化
   |
   v
按照规则进行分块
   |
   v
生成关键词、摘要和向量
   |
   v
写入文档数据库和检索引擎
   |
   v
知识库可以被问答检索
```

### 4.1.1 原始文件保存

文件通常不会直接全部放进 MySQL。系统会把原始文件、附件、页面图片等二进制对象保存到 MinIO 或兼容 S3 的对象存储中。

MySQL 中保存文件的元信息，例如：

- 文件名；
- 文件类型；
- 文件大小；
- 所属用户；
- 所属知识库；
- 上传时间；
- 解析状态；
- 分块数量；
- 处理错误信息；
- 文件在对象存储中的位置。

这样可以避免业务数据库直接承受大量二进制文件，同时也便于文件预览和下载。

### 4.1.2 文档解析

不同文件使用不同的解析器：

- TXT、Markdown：直接读取文本并进行结构分析；
- HTML：提取网页正文和标题层级；
- PDF：解析文字、页面、表格、图片以及版面信息；
- DOCX：解析段落、标题、表格和文档结构；
- XLSX：解析工作表、行列和单元格内容；
- 图片或扫描 PDF：使用 OCR 和 DeepDoc 能力识别文字；
- PPT 或其他格式：根据对应解析器提取文本和结构。

Go 后端的 `internal/parser/`、`internal/deepdoc/` 和 `internal/ingestion/` 是这部分功能的主要代码区域。

### 4.1.3 文本清洗

原始文档通常不能直接用于检索，需要进行处理：

- 清理无意义的空白；
- 合并断行；
- 去除重复页眉页脚；
- 保留标题层级；
- 保留表格关系；
- 记录页码和段落位置；
- 识别图片、公式和代码；
- 保留文件名、章节名等元数据。

这些信息决定了后续检索能否准确命中，以及回答能否给出有效引用。

### 4.1.4 文档分块

一个完整文件可能有几十页甚至几百页，不能一次性全部提交给大语言模型。因此系统会将文档拆分成多个较小的文本块，也称为 Chunk。

分块需要在以下因素之间平衡：

- 块太小：上下文不完整，容易丢失条件和结论；
- 块太大：检索不精确，模型上下文压力大；
- 按固定字数切分：简单，但可能破坏语义；
- 按标题、段落、表格和语义切分：效果更好，但实现复杂；
- 需要保留相邻块关系：方便回答跨段落问题。

铁路资料中尤其需要保留以下结构：

- 设备名称；
- 设备型号；
- 故障现象；
- 故障原因；
- 检查步骤；
- 处理方法；
- 安全要求；
- 禁止操作；
- 适用线路或设备范围；
- 规章版本和生效日期。

### 4.1.5 向量化和索引

系统通常会为每个文本块生成 Embedding 向量。向量是文本语义的数值表示，语义相近的文本在向量空间中距离较近。

例如：

```text
问题：信号机显示异常如何处理？

可能命中的资料：
1. 信号机异常显示故障处理流程
2. 信号设备电源检查方法
3. 信号机灯丝故障案例
```

这些资料不一定包含完全相同的关键词，但语义相近，因此向量检索可以找到它们。

系统同时可以保存关键词索引，用于处理精确型号、设备编号、规章条款号、故障代码等场景。综合使用关键词检索和向量检索就是混合检索。

## 4.2 用户提问流程

一次普通问答的流程如下：

```text
用户输入问题
   |
   v
前端通过 HTTP 或 SSE 发送请求
   |
   v
Go Handler 接收并校验身份、会话和参数
   |
   v
Chat / RAG Service 处理问题
   |
   v
识别问题类型，生成检索词
   |
   v
在指定知识库中检索文本块
   |
   v
对检索结果进行过滤、排序、去重和截断
   |
   v
将问题、历史对话和证据拼接为模型提示词
   |
   v
调用聊天模型
   |
   v
流式返回回答、思考状态、引用和检索信息
   |
   v
前端展示答案、来源和相关文档
```

## 4.3 检索增强生成

RAG 的核心不是让模型直接回答，而是让模型基于检索证据回答。

可以形式化表示为：

```text
Answer = LLM(UserQuestion, ConversationHistory, RetrievedEvidence, SystemPrompt)
```

其中：

- `UserQuestion`：用户当前问题；
- `ConversationHistory`：当前会话的上下文；
- `RetrievedEvidence`：从知识库检索出的文本块；
- `SystemPrompt`：系统身份、回答格式、引用规则和安全规则；
- `LLM`：配置的聊天大语言模型。

当检索不到可靠资料时，系统应该允许模型明确说明资料不足，而不是强行生成一个看似确定的答案。

## 4.4 Agentic RAG

当前 Go 后端不仅支持简单检索，还包含 Agentic RAG 能力。Agentic RAG 会根据问题复杂程度决定下一步动作，例如：

1. 判断用户问题是否需要知识库检索；
2. 将复杂问题拆分成多个子问题；
3. 针对不同资料集进行检索；
4. 发现证据不足时继续检索；
5. 对某个指定文档进行全文摘要；
6. 汇总多轮检索结果；
7. 最后生成带引用的回答。

例如，用户提出：

> 某型道岔在冬季出现转换不到位，可能有哪些原因？请给出排查顺序，并说明哪些操作必须断电。

Agentic RAG 可以将问题拆分为：

- 该型道岔的转换机构和工作原理是什么；
- 转换不到位常见故障原因有哪些；
- 冬季低温对设备有哪些影响；
- 官方检修手册推荐的排查步骤是什么；
- 哪些检查必须断电或设置安全防护；
- 是否有历史故障案例可以参考。

然后将不同检索结果汇总为结构化回答。

## 4.5 引用和证据

系统会在回答中保存或展示来源证据。引用的作用包括：

- 让用户知道结论来自哪份文档；
- 方便打开原文核对；
- 降低无依据回答；
- 支持铁路规章条款的追溯；
- 便于老师或维护人员检查系统是否正确使用资料。

铁路场景建议将引用展示为：

```text
来源：信号设备维护手册
章节：第三章 道岔转换设备
页码：第 42 页
条款：3.4.2
资料版本：2025 年修订版
```

## 5.2 `cmd/`：Go 启动入口

### `cmd/ragflow_server.go`

这是 Go 服务的主要入口，支持不同服务模式：

- `--api`：API 服务；
- `--admin`：管理服务；
- `--ingestor`：文档入库和解析任务服务；
- `--syncer`：数据源同步服务；
- `--deepdoc`：DeepDoc 相关服务；
- `--migrate`：数据库迁移。

服务启动时会完成以下工作：

1. 读取命令行参数；
2. 加载配置；
3. 初始化日志；
4. 初始化数据库；
5. 检查数据库版本；
6. 初始化文档检索引擎；
7. 初始化 Kvrocks；
8. 初始化对象存储；
9. 初始化消息队列；
10. 注册 HTTP 路由；
11. 启动对应服务模式。

### `cmd/ragflow-cli.go`

这是命令行客户端入口，用于通过命令行访问 RAGFlow 的部分能力。

## 5.3 `internal/handler/`：HTTP 请求处理层

Handler 层负责接收 HTTP 请求，是前端和后端业务服务之间的边界。

主要 Handler 包括：

| 文件或类型 | 作用 |
|---|---|
| `user.go` / `auth.go` | 用户登录、注册和身份认证 |
| `dataset.go` | 知识库的创建、修改、删除和查询 |
| `document.go` | 文档上传、解析状态、预览和下载 |
| `chunk.go` | 文档分块查看和处理 |
| `search.go` | 检索测试和搜索接口 |
| `chat.go` | 普通聊天和问答 |
| `bot.go` | Chatbot、Agentbot 对话 |
| `agent.go` | Agent 执行、文件上传、日志和流式结果 |
| `llm.go` / `providers.go` | 模型和模型供应商配置 |
| `memory.go` | 记忆管理 |
| `connector.go` | 外部数据源连接器 |
| `mcp.go` / `mcp_server.go` | MCP 相关能力 |
| `pipeline.go` | 入库 Pipeline 和解析流程配置 |
| `compilation_template.go` | 知识编译模板 |

Handler 不应该承载大量业务规则。它主要负责：

- 解析请求参数；
- 校验身份和权限；
- 调用 Service；
- 将结果转换为 HTTP 响应；
- 对流式消息进行转发。

## 5.4 `internal/router/`：路由注册

`internal/router/` 将 Handler 注册为 API 路由，并区分：

- 无需登录的接口；
- Beta Token 接口；
- 需要用户会话的接口；
- 管理员接口；
- Agent、MCP、文档和聊天接口。

Go API 的主要前缀是：

```text
/api/v1
```

前端通常不会直接在组件中拼接请求细节，而是通过 Service 层统一调用。

## 5.5 `internal/service/`：业务服务层

Service 层是后端最重要的业务实现区域之一，负责组织具体业务流程。

主要业务包括：

- 用户和租户；
- 知识库；
- 文档；
- 文件；
- 分块；
- 聊天会话；
- 模型调用；
- Agent；
- 搜索；
- 记忆；
- 外部连接器；
- 知识编译；
- 任务和日志。

例如，一次聊天请求一般会经历：

```text
Handler
  -> Chat Service
      -> Dataset / Document Service
      -> Retrieval Service
      -> Model Service
      -> Citation Service
  -> Handler 返回结果
```

## 6. 前端请求和状态管理实现

### 6.1 前端启动

前端入口位于 `web/src/main.tsx`。启动时主要完成：

1. 加载语言配置；
2. 请求后端 `/api/v1/language`；
3. 判断当前后端运行方式；
4. 创建 React 根节点；
5. 渲染 `App`。

### 6.2 路由

路由集中在 `web/src/routes.tsx`。页面采用懒加载方式，进入某个页面时才加载对应模块，减少首次加载体积。

### 6.3 请求分层

前端请求大致分为三层：

```text
页面组件
   |
   v
React Query Hook
   |
   v
Service 接口层
   |
   v
Axios / next-request
   |
   v
Go API
```

这样做的好处是：

- 页面不直接拼接复杂 URL；
- 请求缓存和刷新逻辑集中；
- API 类型更清晰；
- 后续修改接口时影响范围较小；
- 可以统一处理登录失效、错误提示和流式响应。

### 6.4 流式回答

聊天和 Agent 通常支持 SSE 流式返回。服务器生成一小段回答后就推送给浏览器，前端逐步显示。

流式返回的优点：

- 用户不用等待整段答案生成完成；
- 可以显示“正在检索”“正在分析”“正在生成”等状态；
- 更适合复杂故障分析；
- 能展示检索证据和 Agent 节点进度。

铁路改造时，可以利用这一能力设计：

```text
正在识别设备类型
正在匹配故障现象
正在检索安全规章
正在检索维修手册
正在分析可能原因
正在生成处理建议
```

## 7. 铁路危险故障解答 AI 改造目标

## 7.1 用户角色

建议至少考虑以下角色：

| 用户角色 | 主要需求 |
|---|---|
| 学生或培训人员 | 学习设备原理、故障现象和处理流程 |
| 现场维修人员 | 快速定位规章、手册和排查步骤 |
| 技术人员 | 对多个故障案例进行分析和对比 |
| 教师或管理员 | 上传资料、维护知识库、检查回答质量 |
| 安全管理人员 | 查看危险操作提示、依据和人工确认点 |

## 7.2 典型问题

系统可以支持以下问题类型：

1. 故障现象解释：
   - “道岔转换不到位通常有哪些原因？”
   - “信号机灭灯可能对应哪些设备问题？”

2. 排查步骤：
   - “出现轨道电路红光带后应该先检查什么？”
   - “如何按照手册顺序检查转辙机？”

3. 安全处置：
   - “检查该设备前是否需要断电？”
   - “哪些操作必须由专人确认？”

4. 规章查询：
   - “相关故障处理的规定条款是什么？”
   - “该规定适用于哪些设备型号？”

5. 案例分析：
   - “过去类似故障是如何处理的？”
   - “这个故障与某案例有什么相同点和区别？”

6. 多资料对比：
   - “2023 版和 2025 版检修要求有什么变化？”
   - “设备说明书和现场规章的处理顺序是否一致？”

7. 教学辅助：
   - “请用学生容易理解的方式解释该设备的工作原理。”
   - “请根据本章节出五道故障判断题。”

## 7.3 推荐的回答结构

铁路故障问题不建议只显示一段普通聊天文本。建议前端将答案结构化展示为：

```text
故障结论
可能原因
建议检查顺序
安全注意事项
禁止或慎用操作
参考依据
不确定性说明
是否需要人工确认
```

示例：

```text
【故障现象】
道岔转换后表示不一致。

【初步判断】
根据当前资料，优先排查机械卡阻、表示杆位置、转辙机表示接点和供电状态。

【建议检查顺序】
1. 确认现场安全条件和设备状态；
2. 按规章要求确认是否需要断电；
3. 检查外部机械阻力；
4. 检查表示杆和连接部件；
5. 检查转辙机表示接点；
6. 对照设备手册进行进一步测试。

【安全提醒】
不得仅依据 AI 回答直接执行现场操作，必须以现行规章、调度命令和现场负责人要求为准。

【参考资料】
《某型道岔维护手册》第三章，第 42 页。
《信号设备故障处理规程》相关条款。
```

## 8. 在基本不改后端的前提下的前端改造方案

## 8.1 总体原则

本项目的主要改造方向是前端，后端尽量复用 RAGFlow 已有能力。

建议遵循以下原则：

1. 不重新开发登录、知识库、文档上传、检索和聊天后端；
2. 不复制一套新的聊天接口；
3. 将铁路资料作为一个或多个专用知识库；
4. 通过前端固定业务入口和默认参数；
5. 通过系统提示词和知识库配置约束回答风格；
6. 通过前端重新组织回答展示；
7. 需要结构化字段时优先利用现有文档元数据和标签；
8. 只有现有 API 无法表达需求时，才评估增加极少量后端接口。

## 8.2 推荐的前端页面结构

可以将现有 RAGFlow 前端改造为以下业务菜单：

```text
铁路危险故障解答系统
├── 首页
├── 智能故障问答
├── 故障案例库
├── 设备资料库
├── 规章制度
├── 我的提问记录
├── 学习与训练
└── 管理中心
```

其中：

- “智能故障问答”复用现有聊天能力；
- “故障案例库”可以复用知识库和搜索页面；
- “设备资料库”可以复用数据集和文件页面；
- “规章制度”可以使用标签、知识库分类和文档筛选；
- “我的提问记录”可以复用聊天会话；
- “学习与训练”可以基于 Agent 或提示词模板；
- “管理中心”保留原有模型、用户和知识库配置。

## 8.3 首页改造

首页不再展示通用 RAGFlow 功能入口，而是突出铁路业务：

### 首页区域

1. 系统标题：
   - 铁路危险故障智能解答系统；

2. 快速提问框：
   - 支持自然语言输入；
   - 支持上传现场图片或故障记录；
   - 支持选择专业类型；
   - 支持选择设备类型；

3. 常用入口：
   - 信号设备故障；
   - 轨道电路故障；
   - 道岔设备故障；
   - 接触网设备故障；
   - 机车车辆故障；
   - 通信设备故障；

4. 安全提示：
   - AI 结果仅供辅助分析；
   - 现场处置必须遵循现行规章和安全流程；

5. 最近问题：
   - 展示当前用户近期的问答；

6. 资料状态：
   - 显示当前已加载的规章、手册和案例资料范围。

## 8.4 智能故障问答页面

建议将页面设计成“三栏结构”：

```text
左侧：问题分类和筛选
中间：对话和故障分析结果

```

### 左侧筛选

- 专业：信号、通信、供电、工务、车辆等；
- 设备类型；
- 设备型号；
- 故障等级；
- 线路或站场；
- 资料范围；
- 资料版本；
- 是否只检索现行规章。

这些字段如果后端不支持专门接口，可以先映射到现有知识库、标签或检索参数。

### 中间问答

主要功能：

- 输入故障现象；
- 上传图片或故障记录；
- 发送问题；
- 流式显示回答；
- 显示分析过程状态；
- 重新生成；
- 继续追问；
- 清空会话；
- 导出分析结果。

### 右侧证据

显示：

- 参考文档名称；
- 章节；
- 页码；
- 匹配片段；
- 资料版本；
- 打开原文；
- 查看前后文；
- 相关案例。

## 8.5 故障分析表单

## 9. 铁路资料接入方案

## 9.1 资料分类

老师提供资料后，建议先进行分类：

```text
铁路资料
├── 国家标准和行业标准
├── 铁路安全规章
├── 设备技术条件
├── 设备说明书
├── 维修规程
├── 作业指导书
├── 故障案例
├── 事故和故障通报
├── 应急预案
├── 培训课件
└── 图片、表格和扫描资料
```

不同类型资料建议进入不同知识库，或者至少使用不同标签。

## 9.2 知识库划分方式

建议优先按“资料用途”划分，而不是一开始按文件夹随意划分。

一种可行方式：

```text
铁路安全规章知识库
铁路设备维护手册知识库
铁路故障案例知识库
铁路应急处置知识库
铁路培训资料知识库
```

如果资料量较小，也可以只建立一个“铁路危险故障综合知识库”，通过标签区分资料类型。

## 9.3 文档命名建议

建议资料统一命名：

```text
[专业][设备][资料类型][版本][状态]文件名.pdf
```

例如：

```text
[信号][道岔转辙机][维修手册][2025版][现行]设备维护手册.pdf
[信号][轨道电路][故障案例][2024][历史]某站故障分析报告.pdf
```

统一命名能够在后端字段不足时，帮助前端和模型识别资料范围。

## 9.4 资料质量要求

资料导入前应检查：

- 是否重复；
- 是否缺页；
- 是否扫描模糊；
- 是否有多个版本；
- 是否明确生效日期；
- 是否包含目录；
- 是否存在水印和页眉；
- 是否为现行版本；
- 是否有保密限制；
- 是否允许作为问答依据。

如果同一规章存在新旧版本，系统必须标识版本和状态，避免模型同时引用互相冲突的内容。

## 10. 提示词和回答约束设计

## 10.1 系统角色建议

铁路场景的系统提示词可以定义为：

```text
你是铁路设备故障分析与规章资料检索助手。
你的任务是根据系统提供的铁路规章、设备手册、维修规程和故障案例，
帮助用户理解故障现象、定位可能原因、整理排查顺序并提供资料依据。

你必须：
1. 优先依据检索到的资料回答；
2. 明确区分资料原文、合理推断和不确定内容；
3. 对涉及人身、行车和设备安全的操作给出安全提醒；
4. 不得把推测表述为确定结论；
5. 资料不足时明确说明需要人工确认；
6. 给出引用来源、章节、页码或文档名称；
7. 不得要求用户绕过规章、调度命令或安全审批流程。
```

## 10.2 回答格式建议

建议统一要求模型输出：

```markdown
## 一、故障现象理解

## 二、初步判断

## 三、可能原因

## 四、建议检查顺序

## 五、安全注意事项

## 六、需要人工确认的内容

## 七、参考依据
```

## 10.3 高风险问题处理

以下问题应强制增加风险提示：

- 是否可以直接操作设备；
- 是否可以跳过断电；
- 是否可以取消防护；
- 是否可以继续行车；
- 是否可以绕过联锁；
- 是否可以临时短接；
- 是否可以改变设备参数；
- 是否可以依据 AI 结果直接恢复设备。

推荐回答策略：

```text
先给出资料层面的分析，
再给出安全边界，
最后明确要求现场人员按照现行规章和正式作业流程确认。
```

## 12. 测试指标建议

铁路场景不能只看“回答是否通顺”，还要关注准确性和安全性。

建议使用以下指标：

### 12.1 检索准确率

问题是否检索到正确资料：

```text
检索准确率 = 命中有效参考资料的问题数 / 总问题数
```

### 12.2 引用正确率

回答中的引用是否真的支持结论：

```text
引用正确率 = 有真实依据的引用数 / 总引用数
```

### 12.3 回答完整度

是否包含：

- 故障原因；
- 检查顺序；
- 安全提醒；
- 人工确认；
- 参考资料。

### 12.4 危险建议率

统计系统是否给出未经依据的危险操作建议。该指标应尽量接近零。

### 12.5 拒答和不确定性质量

当资料不足时，系统是否能够：

- 明确说资料不足；
- 不伪造规章条款；
- 不输出过度确定的结论；
- 引导用户补充设备型号、故障现象和现场条件。

### 12.6 响应速度

关注：

- 首次内容返回时间；
- 完整回答时间；
- 文档检索时间；
- 文件解析时间。

## 13. 需要注意的技术和安全问题

### 13.1 不能把 AI 当作现场决策者

系统回答只能作为辅助信息，不应替代：

- 正式铁路规章；
- 调度命令；
- 现场防护制度；
- 检修负责人判断；
- 设备厂家正式说明；
- 安全审批流程。

### 13.2 资料版本必须可追溯

回答应尽量带：

- 文档名；
- 版本；
- 日期；
- 页码；
- 章节；
- 资料状态。

### 13.3 资料权限必须控制

铁路资料可能包含内部资料、设备参数、线路信息和敏感内容，因此需要保留 RAGFlow 原有的用户、租户、团队和权限机制。

### 13.4 防止提示词注入

上传的文档可能包含“忽略之前指令”等恶意文本。系统应将文档内容视为证据，而不是系统指令。前端不能把文档中的指令直接当成系统规则。

### 13.5 不能只依赖关键词

铁路故障问题中设备型号、专业术语、故障代码和规章条款都很重要。建议同时使用：

- 关键词检索；
- 语义向量检索；
- 元数据过滤；
- 文档版本过滤；
- 相关性排序；
- 引用核验。

### 13.6 OCR 结果需要复核

扫描资料的 OCR 可能把型号、数字、单位和条款号识别错误。对于重要规章，应抽样检查 OCR 结果，必要时保留图片页作为引用依据。

## 16. 结论

RAGFlow 已经具备建设铁路危险故障解答 AI 所需要的大部分底层能力，包括文档上传、文档解析、知识库、文本切片、向量检索、混合检索、模型调用、流式回答、Agent 工作流和引用展示。

因此，本项目不需要从零开发一个大语言模型系统，也不需要重新实现文档解析和检索。更合理的路线是：

```text
保留 RAGFlow 的后端能力
        +
导入铁路规章、手册、案例和培训资料
        +
设计铁路专用提示词和回答规范
        +
重点改造 React 前端页面和交互
        =
铁路危险故障解答 AI
```

第一版建议聚焦“资料检索和故障解答”，不要一开始就做过于复杂的自动诊断或自动控制。系统首先要做到：

1. 找得到正确资料；
2. 说得清故障原因；
3. 给得出有依据的排查顺序；
4. 显示完整引用；
5. 明确安全边界；
6. 资料不足时能够诚实说明；
7. 让用户能够快速、方便地使用。

等老师提供资料并确定具体铁路专业、设备范围和展示要求后，可以进一步细化：

- 知识库分类；
- 文件命名；
- 资料标签；
- 故障表单字段；
- 页面原型；
- 提示词；
- 评价题库；
- 测试问题集；
- 最终答辩演示流程。
